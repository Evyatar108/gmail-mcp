# MCP tool reference

All tools return structured JSON. Gmail resource IDs are opaque strings and
should be passed between tools unchanged.

## Read tools

| Tool | Important inputs | Result | Limits |
| --- | --- | --- | --- |
| `gmail_search` | `query`, `page_size`, `page_token`, `include_spam_trash` | Message IDs, thread IDs, labels, selected headers, snippets, next-page token | 1-50 results; default 20; Spam/Trash included by default |
| `gmail_get_message` | `message_id`, `max_body_chars`, `max_attachments` | Selected headers, bounded body, labels, snippet, attachment metadata | Body 0-50,000 chars; attachments 0-100 |
| `gmail_get_thread` | `thread_id`, `max_messages`, `max_body_chars_per_message` | Ordered normalized messages and truncation flag | 1-50 messages; each body 0-50,000 chars |
| `gmail_list_labels` | None | System and user label metadata | Gmail response |
| `gmail_list_filters` | None | Filter IDs, criteria, redacted actions, safe-delete indicator | Forwarding addresses are never returned |
| `gmail_list_attachments` | `message_id`, `max_items` | Filename, MIME type, size, part ID, attachment ID | Metadata only; 0-100 |

Search uses standard Gmail query syntax, for example:

```text
newer_than:7d
from:example.com has:attachment
subject:(receipt OR invoice) after:2026/01/01
label:inbox is:unread
```

Search returns snippets, which can contain sensitive text. Retrieve full message
bodies only when needed.

## Local file creation

| Tool | Inputs | Effect | Limits |
| --- | --- | --- | --- |
| `gmail_download_attachment` | `message_id`, exact MIME `part_id`, absolute existing `destination_directory`, optional `max_bytes` | Saves one selected attachment locally and returns metadata/path only | No overwrite or directory creation; 1 byte-25 MiB; MIME parts without `attachmentId` are unsupported |

Use the `part_id` returned by `gmail_list_attachments`; Gmail attachment IDs are
transient and can change between metadata reads. The server resolves the selected
part against a fresh full message and uses its current attachment ID internally.
Gmail filenames are untrusted and are normalized into one safe Windows filename;
path components, control characters, reserved device names, and trailing
dots/spaces are removed or replaced. A name collision fails rather than
overwriting or auto-renaming. The destination may be a resolved junction/symlink,
but the final file must stay inside that resolved directory.

Attachment bytes travel directly from Gmail to the local server process and are
not returned in MCP output. The saved file is still untrusted and may contain
sensitive data; do not open, execute, publish, or commit it without a separate
operator request.

## Reversible mutation tools

| Tool | Inputs | Effect | Limit |
| --- | --- | --- | --- |
| `gmail_create_label` | `name`, optional visibility settings | Creates a user label | 225-character name |
| `gmail_modify_labels` | `message_ids`, `add_label_ids`, `remove_label_ids` | Batch add/remove labels | 100 messages and 100 labels |
| `gmail_archive` | `message_ids` | Removes `INBOX` | 100 messages |
| `gmail_create_draft` | `to`, `body`, optional `subject`, `cc`, `bcc`, `reply_to_message_id`, `rtl` | Creates a draft; `rtl=true` adds escaped right-aligned HTML plus plain-text fallback; never sends | 50 recipients, 998-char subject, 200,000-char body |
| `gmail_untrash` | `message_ids` | Restores messages while Gmail retains them | 100 messages |

`gmail_modify_labels` rejects `TRASH` and `SPAM`. Use the dedicated tools for
Trash transitions; spam reporting is intentionally not exposed.

Reply drafts resolve the source message, Gmail thread ID, RFC-822 `Message-ID`,
`In-Reply-To`, and `References`. A caller-supplied reply subject must remain
compatible with the source thread.

Raw MIME, caller-provided HTML, HTML-only bodies, and attachments are not
accepted for drafts. RTL HTML is generated by the server from escaped plain text.

## High-impact tools

### `gmail_create_filter`

Supports sender, recipient, subject, query, negated query, attachment/chat
modifiers, and paired size comparison. Safe actions are user-label application,
archive, mark read, and star.

The first call returns a normalized preview and a one-time
`CREATE_FILTER ...` token valid for ten minutes. Review the future-mail behavior
and approve the native destructive-tool prompt before repeating the call.

Forwarding, Trash/Spam automation, arbitrary system labels, broad modifier-only
rules, and query-only archive/mark-read rules are rejected.

### `gmail_delete_filter`

The first call returns the current redacted filter and a one-time
`DELETE_FILTER ...` token. Filters containing forwarding or unsafe actions must
be deleted manually in Gmail settings.

### `gmail_send_draft`

Input:

```json
{
  "draft_id": "DRAFT_ID",
  "confirmation": null
}
```

The first call returns:

```json
{
  "status": "confirmation_required",
  "preview": {
    "draft_id": "DRAFT_ID",
    "recipients": {"to": ["recipient@example.com"], "cc": [], "bcc": []},
    "subject": "Subject"
  },
  "confirmation": "SEND DRAFT_ID STATE_FINGERPRINT"
}
```

Review the preview with the operator. Only after explicit approval should the
exact confirmation string be supplied in a second call. The server re-fetches
the draft, so edits invalidate the token.

### `gmail_trash`

Input:

```json
{
  "message_ids": ["MESSAGE_ID"],
  "confirmation": null
}
```

The first call returns current From/Subject/Date metadata and:

```text
TRASH STATE_FINGERPRINT
```

After explicit approval, repeat the call with the exact token. The maximum is 20
message IDs. Thread IDs are not accepted. Partial failures trigger an attempted
rollback with `untrash`.

## MCP annotations

| Category | Tools | Annotation intent |
| --- | --- | --- |
| Read-only | Search, get message/thread, labels, filters, attachment metadata | `readOnlyHint=true` |
| Mutating | Attachment download, create/apply labels, archive, draft creation, untrash | `readOnlyHint=false`, `destructiveHint=false` |
| High impact | Create/delete filter, send draft, Trash | `destructiveHint=true` |

Annotations inform the client but are not an authorization boundary. Keep
Copilot confirmations enabled and follow the safe-use skill.
